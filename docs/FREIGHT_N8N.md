# Freight RFQ — n8n automation

**Status: built and tested against a simulated adapter. Not yet run against a
real n8n instance** — none was available. The endpoints are real and covered by
tests; the workflow exports are real and importable. What has not happened is a
live import into someone's n8n. The checklist at the end is for that.

---

## 1. The division of labour

This follows the split already set out in `docs/N8N_INTEGRATION.md` for the
operations module, applied to freight.

| | Owned by **Mobility Pro Command** | Owned by **n8n** |
| --- | --- | --- |
| Deciding a provider is due a chase | ✅ | |
| Knowing what time it is, and running on a schedule | | ✅ |
| Writing what the reminder says | ✅ | |
| Telling the manager something is waiting | | ✅ |
| Deciding whether an ERPNext retry is safe | ✅ | |
| Retrying on a timer | | ✅ |
| Deciding whether anything may be sent | ✅ | |
| Delivering a notification to Slack or email | | ✅ |

**Rules live in the application** because they are deterministic, versioned with
the code and covered by tests. Change the chase policy and a test tells you what
moved.

**I/O lives in n8n** because it changes often, it is where credentials for Slack
and Teams belong, and the client's own team can edit a workflow without waiting
for a deployment.

The failure mode to avoid is putting the policy inside n8n nodes. "Chase after
three days, at most twice" scattered across a workflow is untestable, invisible
to the person who owns the policy, and impossible to reconcile when two
workflows disagree. So `src/freight/domain/chasing.ts` decides, and the workflow
asks.

> Before this work the reminder settings in the UI were **decorative** — stored
> and displayed, but nothing read them. They now drive the chase policy.

## 2. The hard boundary

**No workflow can send an email to a provider, and no workflow can approve one.**

That is not a convention or a code review rule. Automation runs as a
`system_automation` identity which:

- `assertCanApprove` refuses, so it cannot approve;
- `assertCanSend` refuses, so it cannot send — **even an email a person has
  already approved**;
- is never written to the users table, so it cannot be selected in "Acting as".

There is a test that approves an email as a manager and then tries to send it as
automation. It must fail, and it does.

What automation *may* do is prepare a draft reminder and retry a failed ERPNext
record. Both are recoverable, and both leave the decision with a person: the
draft sits in the approval queue with its recipients and body visible.

## 3. The endpoints

All under a single bearer token, `FREIGHT_AUTOMATION_TOKEN`. **With no token set
they return 404**, which is the safe default for a surface that reaches every
company's data. The token is separate from `MAILBOX_COLLECT_TOKEN` so either can
be rotated without the other.

| Call | Purpose | Writes? |
| --- | --- | --- |
| `POST /api/freight/collect` | Collect replies from the shared mailbox | files replies |
| `GET /api/freight/automation/summary` | One-call summary for a briefing | read-only |
| `GET /api/freight/automation/approvals` | What is waiting for approval, longest wait first | read-only |
| `GET /api/freight/automation/reminders` | Which providers are due a chase, and why | read-only |
| `POST /api/freight/automation/reminders` | Prepare draft reminders | drafts only |
| `GET /api/freight/automation/erpnext` | Records that have not reached ERPNext | read-only |
| `POST /api/freight/automation/erpnext` | Retry what can safely be retried | retries |

They are also listed in the application under **Settings → Scheduled
automation**, so the seam is visible to whoever is looking at the screen rather
than only to whoever reads this file.

Every endpoint returns `{ ok, message?, data }` and never leaks an internal
error message to an external caller.

## 4. The workflows

Five exports in `public/n8n/`, generated by
`scripts/build-freight-workflows.mjs` so they stay consistent with each other.
**Re-run that script after changing an endpoint path** — it validates that every
URL a workflow calls resolves to a route that actually exists in this
repository, that every node is reachable from its trigger, and that each export
is inactive.

| File | Schedule | What it does |
| --- | --- | --- |
| `freight-reply-collection.json` | every 15 min | Collects replies. Raises a transport failure; an unmatched reply is a normal outcome and waits for a person. |
| `freight-deadline-chaser.json` | weekdays 09:00 | Asks who is due, prepares drafts, tells the manager they are waiting. |
| `freight-approval-nudge.json` | every 3h, office hours | Nudges the manager about the approval queue, including approvals that lapsed after an edit. |
| `freight-erpnext-retry.json` | hourly | Retries failed records; escalates ones blocked on setup instead of retrying forever. |
| `freight-daily-briefing.json` | weekdays 08:00 | One summary call, posted only when there is something to report. |

The `noOp` nodes named "Nudge the manager", "Post the briefing" and "Raise to
operations" are deliberate placeholders: the destination is Slack, Teams or
email depending on the client, and the credential belongs in their instance.
Replace the node, keep the wiring.

Exports land **inactive**. A workflow that started running the moment it was
imported would chase real providers from someone's test instance.

## 5. The chase policy

`src/freight/domain/chasing.ts`, driven by **Settings → Chasing non-responders**.

A provider is due when all of these hold:

- the request is still collecting;
- they were sent the RFQ and have not replied or declined;
- the response deadline has not passed;
- they have had fewer than `maxRounds` reminders;
- `afterDays` have passed **since the last contact** — the original send, or the
  previous reminder, whichever is later.

Every answer carries its reason, so a workflow can log why a provider was left
alone rather than the operator guessing. The deliberate choices:

- **Chasing stops at the deadline.** After it, the manager closes collection and
  compares what arrived; chasing then only annoys the provider.
- **A failed send is never chased.** Reminding someone about a message they
  never received is worse than useless — fix the send.
- **`maxRounds: 0` switches chasing off** without needing a separate flag.

## 6. Running a local n8n

For trying the workflows without touching a client instance.

```bash
# 1. Tokens for this application
cp .env.example .env.local        # then fill in the two tokens, or:
node -e "const{randomUUID:u}=require('node:crypto');console.log('FREIGHT_AUTOMATION_TOKEN='+(u()+u()).replace(/-/g,''))"

# 2. Start this application
npm run build && npm start        # http://localhost:4310

# 3. Start n8n (installed outside this repo so it stays out of package.json)
mkdir -p ../n8n-host && cd ../n8n-host && npm init -y && npm install n8n
N8N_PORT=5678 N8N_DIAGNOSTICS_ENABLED=false N8N_VERSION_NOTIFICATIONS_ENABLED=false   npx n8n start                   # http://localhost:5678

# 4. Provision it from the repo
npm run n8n:provision
```

`npm run n8n:provision` creates the owner account, creates both Header Auth
credentials, regenerates the workflows with **literal URLs** and imports them
with the credentials already attached. It is idempotent — run it again after
changing a workflow and it updates rather than duplicating.

> **Why literal URLs.** n8n *Variables* are a licensed feature, so
> `{{ $vars.MPC_BASE_URL }}` does not resolve on the community edition. The
> committed exports keep `$vars`, which is right for a licensed instance;
> the provisioner regenerates them with
> `--base-url=... --out=scripts/.n8n-workflows` for a community one.

Defaults, all overridable by environment variable: `N8N_URL`
`http://localhost:5678`, `MPC_BASE_URL` `http://localhost:4310`, `N8N_EMAIL`
`freight@mobilitypro.test`, `N8N_PASSWORD` `FreightRfq2026`.

The provisioner uses n8n's **internal** REST API — the one its editor uses —
because the public API needs an API key, which you can only get by logging in
first. That is fine for a local instance you control; it is not a supported
integration point and may change between n8n versions.

## 7. Setup against a client instance

```bash
# .env.local
FREIGHT_AUTOMATION_TOKEN=<a long random string>
MAILBOX_COLLECT_TOKEN=<a different long random string>
```

In n8n:

1. **Variable** `MPC_BASE_URL` → where this application is reachable from n8n.
2. **Credential** of type *Header Auth*, name `Authorization`, value
   `Bearer <FREIGHT_AUTOMATION_TOKEN>`. A second one for the collection token.
3. Import the five files, attach the credential to the HTTP nodes, replace the
   placeholder notification nodes, then activate one at a time.

## 8. Live test checklist

Nothing below has been done — there was no instance to do it on.

| # | Step | Expected | Result |
| --- | --- | --- | --- |
| 1 | Import all five | They import inactive, no missing-node warnings | |
| 2 | Run *Daily briefing* manually | 200, counts match the Overview screen | |
| 3 | Unset the token, run again | 404 and a message saying automation is switched off | |
| 4 | Wrong token | 401 | |

| 6 | Run *Deadline chaser* with a provider past the policy | Drafts appear in the approval queue, **nothing sent** | |
| 7 | Run it again immediately | 0 prepared, the providers reported as skipped | |
| 8 | Check the activity trail | Entries attributed to "Scheduled automation" | |
| 9 | Run *ERPNext retry* with a failed record | It recovers, attempts increments, no duplicate | |
| 10 | Run *Reply collection* | Replies filed; a second run files nothing twice | |
| 11 | Try to send from a workflow | There is no endpoint that can. Confirm none was added | |

Step 11 matters most. If a future endpoint ever makes it possible for a workflow
to send, the approval guarantee this whole module is built around is gone.

## 9. What is not built

- **Notification delivery.** The workflows stop at a placeholder; the Slack or
  Teams node is the client's to add, with their credential.
- **A live n8n adapter.** The Automations screen in the operations module still
  shows `DemoN8nAdapter` with invented runs. Nothing on the freight side claims
  otherwise — freight simply exposes endpoints and does not track n8n runs.
- **Webhooks from n8n into a specific RFQ.** Everything is pull-based on a
  schedule, which is simpler and has no inbound surface to secure beyond the
  token.
